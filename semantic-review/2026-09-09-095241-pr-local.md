# Optional custom-domain support for the Amplify-hosted frontend

Adds an optional `WREN_CUSTOM_DOMAIN` env var that maps the Amplify production branch to a custom domain root and its `www` subdomain. The value threads from `parseDeploymentConfig` through `cdkContextArgs` into `resolveAppConfig` and finally `AmplifyStack.addDomain`, which uses the `@aws-cdk/aws-amplify-alpha` domain-association API and emits a `CustomDomainUrl` output. No Route 53 or ACM resources are created, keeping the feature DNS-provider/account-agnostic. The deploy workflow prefers the custom domain for the hosted-app log, signup guidance, and the smoke-test origin, with a reachability-based fallback to the Amplify default domain for the smoke test. When the var is unset, the `customDomain` key is omitted from config and the stack synthesizes nothing new.

Watch for: the signup-guidance URL prefers the custom domain but has no reachability fallback (confirmed), unlike the smoke test — during cert provisioning it points admins at a non-live host. The diff also bundles two unrelated changes: a TipTap field size limit bump from 1MB to 8MB and a related error-message tweak (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The threading is symmetric: every hop uses the same conditional-spread pattern (`...(customDomain ? { customDomain } : {})`), so an unset domain never introduces a config key, a context arg, or a synthesized resource. The regression guarantee holds and is locked by a test asserting zero `AWS::Amplify::Domain` resources and no `CustomDomainUrl` output when unset.

`addDomain(config.customDomain)` passes the hostname as the construct id, which the alpha `Domain` construct resolves as the domain name; `mapRoot` and `mapSubDomain(..., "www")` produce the root + www associations, and no ACM/Route 53 constructs are introduced.

The smoke test probes the custom domain and on any failure (including cert-not-live) falls back to the always-available Amplify default, with wildcard API CORS making either origin valid. The signup-guidance path reuses `primaryFrontendHost` but without the reachability check, so during provisioning it can hand an admin a not-yet-live URL.

The checkpoint fingerprint intentionally incorporates the domain via `publicDeploymentConfig`, so changing the domain forces reconfirmation — a deliberate choice, documented inline and covered by a test.

### Signup-guidance URL has no reachability fallback

`verifyOrCreateAdmin` computes `signupDomain = primaryFrontendHost(this.config.customDomain, amplify.outputs.AmplifyDefaultDomain)` and, when no confirmed user exists, tells the admin to `Sign up at https://${signupDomain}/signup` (`deployWorkflow.ts` ~line 1013). `primaryFrontendHost` returns the custom domain whenever it's set — with no reachability probe. During the cert/DNS provisioning window (which the docs and the hosted-app log both acknowledge can take several minutes), this guidance points the admin at a host that returns a TLS or NXDOMAIN error, even though the Amplify default is live and would work.

This is the same window the smoke test explicitly guards against, so the two paths are inconsistent: the smoke test falls back, the signup guidance does not. The admin-signup step is exactly when a human is most likely to hit the URL by hand. Either probe reachability the way the smoke test does, or prefer the Amplify default for the signup URL specifically. (confirmed)

### Amplify domain association: dotted hostname as construct id

`this.amplifyApp.addDomain(config.customDomain)` passes the hostname as the construct `id`, and `Domain` resolves `domainName = props.domainName || id` (verified against `node_modules/@aws-cdk/aws-amplify-alpha/lib/domain.js:135` and `app.js:305`). A side effect is that the logical id derives from the domain string, so changing the domain replaces the association resource rather than updating in place — correct for a domain change, but worth knowing since it means a domain edit is a resource replacement, not a mutation. (confirmed)

### Hostname validation has no per-label length cap

`validateCustomDomain` requires two or more dot-separated lowercase labels, each `[a-z0-9]` with optional internal hyphens, no leading/trailing hyphen, total length ≤ 253, no scheme/path/trailing dot. The negative-case test table exercises scheme, uppercase, space, path, trailing dot, single label, and leading hyphen.

The gap: there is no per-label length cap. Amplify's own `Domain` validation enforces ≤ 62 chars per label (`domain.js:139`), so a label of 64+ chars passes WREN's check and then fails later during synth with a less friendly CDK error. Low severity — the failure is still caught before deploy, just further down the stack. Optional to tighten by bounding each label to `{1,63}`. (confirmed)

### Unrelated changes bundled in

Two edits in this diff have nothing to do with custom domains:

- `types/src/tiptapContent.ts`: `TIPTAP_FIELD_MAX_BYTES` changes from `1_048_576` to `8 * 1_048_576` (1MB → 8MB).
- `backend/document/src/lambda-handler.ts`: the payload-too-large message switches from a hard-coded `1MB` to a computed `${Math.round(TIPTAP_FIELD_MAX_BYTES / 1_048_576)}MB`.

The handler change tracks the constant, but the pair is a behavioral change to request-size limits unrelated to frontend hosting. Bundling it obscures the diff's intent and couples an 8x increase in accepted payload size — which has memory/throughput implications on the document Lambda — to a hosting feature. Split it out so it can be reviewed and reverted independently. (confirmed)

### Test coverage

Covered: threading (config parse both states, context-arg presence/absence, `resolveAppConfig` mapping), the stack's domain-set and domain-unset (regression) cases, `primaryFrontendHost` precedence across all four input combinations, malformed-domain rejection table, public-config echo, and fingerprint change.

Not tested: the signup-guidance URL selection and the smoke-test reachability fallback (the `reachable`/fallback branch in `runSmokeTest` and the not-live-yet path in `verifyOrCreateAdmin`). A test asserting which host the signup guidance emits when the custom domain is set would have surfaced the asymmetry flagged above. (confirmed)
