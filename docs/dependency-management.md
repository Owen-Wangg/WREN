# Dependency Management Guide

## Overview

This document explains how **Node.js** and **Python** dependencies are declared, pinned, and shipped in WREN.

| Workload | Language | How dependencies are installed |
| --- | --- | --- |
| Shared types, auth, admin, document, feedback, notification | Node 22 | npm workspaces + root `package-lock.json`; CDK **esbuild** bundles Lambdas |
| Frontend (React web app) | Node (Vite) | `frontend/package.json` + `frontend/package-lock.json` |
| CDK app | Node | `cdk/package.json` + `cdk/package-lock.json` |
| Feedback Engine | Python 3.12 **container** | `pip install` in `backend/engine/python/Dockerfile` from a uv-compiled lockfile |
| Diff / Anchor / Progress Lambda | Python 3.12 zip | **Standard library only** — no `requirements.txt` on the function |
| Engine + DB Python tests | Python 3.12 | **uv** (`pyproject.toml`, `uv.lock`) |

Steering (UBC CIC): pin dependencies and commit lock files (`package-lock.json` for Node; `uv.lock` / compiled `requirements.txt` for Python). Prefer exact pins (`==`) in files that install at deploy or container build time.

## Node.js (monorepo)

### Workspaces (repository root)

Root `package.json` workspaces:

- `types` (`@wren/types`)
- `backend/database/node` (`@wren/db-node`)
- `backend/auth`, `backend/admin`, `backend/document`, `backend/feedback`, `backend/notification`

Install from the **repository root** so workspace packages hoist into root `node_modules`:

```bash
npm ci
```

Commit **`package-lock.json`** at the repo root. Do not rely on `npm install` without updating the lockfile in PRs.

Workspace packages depend on each other with `"@wren/types": "*"` (and similar). Shared runtime validation uses **Zod** (also listed on the root package).

### Lambda bundling (Compute stack)

Node Lambdas are `NodejsFunction`s. esbuild runs with `projectRoot` = monorepo root and `depsLockFilePath` = root `package-lock.json`, so `@wren/*` resolves through workspace links.

- Default: minify + source maps, target `node22`. Dependencies are **bundled into the artifact** (not Lambda layers).
- **Document Lambda** is special: `pdfjs-dist` and `pdf-parse` are listed in `nodeModules` so they ship as real `node_modules` (workers/ESM). Do not esbuild those packages into a single file.

If a new npm package must stay unbundled (native addons, worker files), add it to that `nodeModules` array in `cdk/lib/stacks/ComputeStack.ts`.

Do **not** mark `@wren/db-node` as an esbuild `externalModule` unless you also ship a layer — that combination failed at runtime on the first deploy.

### Frontend

```bash
cd frontend
npm ci
```

Lockfile: `frontend/package-lock.json`. Amplify builds use this package independently of the CDK lockfile.

### CDK package

```bash
cd cdk
npm ci
```

Lockfile: `cdk/package-lock.json`. This is **not** an npm workspace of the root package; install it separately after root `npm ci` (Compute bundling still needs root `node_modules` for `@wren/*`).

## Python

Python **3.12** is required (`requires-python = ">=3.12"` in root `pyproject.toml`).

### uv (tests and compile)

Root `pyproject.toml` is test tooling (`package = false`). Dev group: pytest, Hypothesis, `psycopg[binary,pool]`.

```bash
# from repository root
uv sync
uv run pytest
```

Lockfile: **`uv.lock`** (commit it).

Compile a pinned install file from a `.in` manifest:

```bash
uv pip compile backend/engine/python/requirements-feedback-engine.in \
  -o backend/engine/python/requirements-feedback-engine.txt \
  --python 3.12
```

Use the same pattern for `backend/engine/python/requirements.in` → `requirements.txt` (test-only engine toolchain) and `backend/database/python/requirements.in` → `requirements.txt`.

### Feedback Engine container (the heavy Python runtime)

**Location:** `backend/engine/python/`  
**Runtime:** AWS Lambda Python 3.12 **container image** (`public.ecr.aws/lambda/python:3.12`)  
**Image tag Compute expects:** `{stackPrefix}-feedback-engine:bootstrap`

This is the only Python workload that needs a **runtime** third-party stack (Bedrock via `langchain-aws`, Postgres via `psycopg`).

**Declare** packages in `requirements-feedback-engine.in` (direct deps only):

| Package | Pinned in `.in` | Purpose |
| --- | --- | --- |
| `langchain-aws` | `1.0.0` | `ChatBedrockConverse` — model-agnostic Bedrock calls |
| `langchain-core` | `1.4.9` | Required by langchain-aws |
| `boto3` | `1.40.63` | AWS SDK (meets langchain-aws `boto3>=1.40.19`) |
| `psycopg[binary]` | `3.3.4` | PostgreSQL via RDS Proxy |

**Lock** the full tree in `requirements-feedback-engine.txt` (autogenerated by uv). The Dockerfile installs **that** file:

```dockerfile
COPY requirements-feedback-engine.txt .
RUN pip install -r requirements-feedback-engine.txt --target "${LAMBDA_TASK_ROOT}"
```

Changing the Bedrock **model id** does **not** require a new Python package (REQ-NFR-MODEL-01). Changing **invocation libraries** does.

Diff / Anchor / Progress **core** (`difflib`, remap, progress) stays stdlib-only and is **not** installed from this file.

### Engine test pin file

`backend/engine/python/requirements.in` → `requirements.txt` is **pytest + Hypothesis** for local/CI engine tests. It is **not** copied into the Feedback Engine image.

### Python data-access package

`backend/database/python/` (`wren_db`): `psycopg[binary,pool]`. `boto3` is omitted in `.in` because the Lambda Python **runtime** already provides it when this code runs on a zip Lambda; the Feedback Engine image still installs boto3 via the engine lockfile.

### Diff / Anchor / Progress zip Lambda

`cdk/lambda/diff-anchor-progress/` is `lambda.Code.fromAsset` with **no pip install**. Do not add third-party imports there without switching to a layer or container.

The function is created in `ComputeStack` and included in Observability log retention. It is **not** attached to API Gateway; live remapping runs inside the Feedback Engine (`wren_engine`), not this zip handler.

`backend/engine/python/requirements.txt` is the **test** compile of `requirements.in`. It still contains leftover comments/`boto3`/`psycopg3` lines that are **not** installed by the Dockerfile. Treat `requirements-feedback-engine.txt` as the runtime lockfile.

## Adding a New Dependency

### Node (workspace Lambda or shared package)

1. Add the package to the relevant workspace `package.json` (or root, if truly shared).
2. From repo root: `npm install <pkg> -w @wren/<workspace>` (or edit JSON and `npm install`).
3. Commit the updated `package.json` and **root** `package-lock.json`.
4. Redeploy Compute (`npx cdk deploy wren-dev-Compute`) so esbuild picks it up.
5. If the package cannot be bundled, add it to `nodeModules` in `ComputeStack.ts`.

### Frontend

1. `cd frontend && npm install <pkg>`
2. Commit `frontend/package.json` and `frontend/package-lock.json`.
3. Amplify rebuild (or local `npm run build`).

### CDK constructs

1. `cd cdk && npm install <pkg>`
2. Commit `cdk/package.json` and `cdk/package-lock.json`.
3. `npx cdk deploy …`

### Feedback Engine (Python runtime)

1. Add a **pinned** line to `backend/engine/python/requirements-feedback-engine.in`:

   ```
   some-package==1.2.3
   ```

2. Recompile:

   ```bash
   uv pip compile backend/engine/python/requirements-feedback-engine.in \
     -o backend/engine/python/requirements-feedback-engine.txt \
     --python 3.12
   ```

3. Rebuild and push the image (see [deployment-guide.md](./deployment-guide.md) Step 4):

   ```bash
   docker build -t "${ACCOUNT}.dkr.ecr.ca-central-1.amazonaws.com/wren-dev-feedback-engine:bootstrap" \
     backend/engine/python/
   docker push …:bootstrap
   ```

4. Point the Lambda at the new image (`update-function-code` or the CI/CD UpdateLambda stage). Deploying Compute **alone** does not rebuild pip packages inside an existing `bootstrap` tag.

5. Confirm `/aws/lambda/wren-dev-feedback-engine` starts (`handler.handler`) and Bedrock/DB still work.

### Engine or DB Python tests only

1. Edit `requirements.in` or `pyproject.toml` `[dependency-groups] dev`.
2. `uv lock` / `uv pip compile` as appropriate.
3. Commit `uv.lock` and any regenerated `requirements.txt`.
4. No image push required.

## Updating an Existing Dependency

**Node:** bump the version in `package.json`, run `npm update` / `npm install` in the right tree, commit the lockfile, redeploy the consumer (Compute, Amplify, or CDK).

**Python runtime:** bump the pin in `requirements-feedback-engine.in`, recompile `.txt`, rebuild/push `bootstrap`, update the Lambda.

Always pin **exact** versions in `.in` files that feed production installs (`==`). Unpinned ranges can change between `uv pip compile` runs and between Docker builds.

After a `langchain-aws` bump, re-check the required `boto3` floor and IAM (CRIS model ARNs in `ComputeStack.ts`) — a new model **family** may need IAM even if pip succeeded.

## CI/CD

When GitHub context is set, CodePipeline **Build_And_Test** can produce a new engine image URI and **UpdateLambda** rolls the Feedback Engine. Local/manual flow is Docker build + ECR push + `lambda update-function-code` as in the deployment guide.

Node tests: root `npm test` (Jest). Frontend: `npm test` in `frontend/` (Vitest). Python: `uv run pytest`.

## Troubleshooting

| Symptom | What to check |
| --- | --- |
| Lambda `Cannot find module '@wren/…'` | Root `npm ci` before CDK deploy; esbuild `projectRoot` is monorepo root; package not marked external |
| PDF extract fails in Document Lambda | `pdfjs-dist` / `pdf-parse` still in `nodeModules` bundling options |
| Engine import error / missing langchain | Image was built from an old `requirements-feedback-engine.txt`; rebuild `bootstrap` |
| `psycopg` vs `psycopg2` | Engine uses **psycopg 3** (`psycopg[binary]`), not `psycopg2-binary` |
| Glue / `msgraph-sdk` | Not used in this repo |
| Two different `boto3` pins | Engine **test** `requirements.txt` vs **runtime** `requirements-feedback-engine.txt` are separate; the container uses the latter |
